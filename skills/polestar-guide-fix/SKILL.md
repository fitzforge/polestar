# Fixing a step in Polestar's guides

`polestar` below is `node tools/polestar.js` in the clone (`find`,
`playtest`, `changelog` and `regen` are still current; lint is `forge guide lint`); `forge` is Polestar
Forge (docs/FORGE.md). CONTRIBUTING.md ("Fixing a guide", "Branches") is the
long form; docs/GUIDE_CHEATSHEET.md has the guide format on one page.

## 0. Is it confirmed?

Fix only what you have shown is wrong. If the bug came from a report and
nobody has checked it yet, run the polestar-triage skill
(`skills/polestar-triage/SKILL.md`) first. A fix needs a verdict of
"confirmed" or "partly right" and the evidence behind it.

Then make sure no one is fixing it already: the issue's "Pull requests for
this issue" comment (label `has-pr`), and
`gh pr list --state open --search "<issue number>"`, then the quest id. An
open pull request that covers it means you help on that one instead
(polestar-contributing, "Before you start on an issue").

## 1. Pick the branch

Every fix starts from `next`, and its pull request goes to `next`:

```sh
git fetch origin
git switch -c fix/<short-name> origin/next
```

Every fix goes to `next`. Never open a pull request against `main`.

## 2. Find the step and read why it is there

```sh
git grep -n "accept 184" guides/
polestar find 184
```

Read the comments at the top of the guide before moving anything. They say
where the route comes from and why it goes the way it does. A fix that
changes the route updates them too, so a later route refresh keeps it.
Routes are refreshed by Polestar Forge (`forge build`, docs/FORGE.md), which
starts from the guides' own order; an order players asked for that a
refresh must keep gets its case in `tests/guides-reported.test.js` and the
same pair under `deliberate` in `data/route-fixes.json` (Forge's hard
orders); a quest to always include or leave out goes under `overrides` in
the same file (docs/forge/routes.md#11-overrides).

## 2b. Name the pattern and sweep for it

A confirmed report is one instance of a pattern. Before fixing it, name the
pattern in one line, for example "the first accept sends you past a giver
standing next to you" or "an `interact` goal for an objective that is
really a cast or /sit". Then look for the same thing in every guide, the
other faction's counterpart and the code path behind it (`git grep` on the
verb or quest pattern, `forge guide lint`). Fix every real instance together,
or list the rest on the issue. The fix, its test and its changelog entry
cover the pattern, not only the step that was reported.

## 3. Make the change

**First: is the guide generated?** Look at the guide's first line and at
`guides/GENERATED.json`:

- **Before the Forge cutover** (no `guides/GENERATED.json`, no guide starts
  with `# Generated by forge build`): every guide is hand-edited on `next`.
  Fix the `.guide` as below. The cutover seeds Forge from `next`, so the edit
  is kept. A data fact still goes in its record too (table below).
- **After the cutover** the leveling guides under `guides/forever/alliance/`
  and `guides/forever/horde/` start with `# Generated by forge build` and are
  listed in `guides/GENERATED.json`. Never edit those (CI fails the pull
  request, and the next build would undo it). Class, professions,
  reputation, collectibles, exploration, dungeon and lookup guides stay
  hand-written.

For a generated guide, put the fix in the record every build applies. Every
correction needs a `source` (`{ "kind": "in-game-check", "ref": "#699" }`;
the kinds are in the file's `_about`) and a `note` in your own words, or
`forge data check-corrections` fails. Cite issues, recordings and in-game
checks, never a website.

| The fix | Where |
|---|---|
| a quest fact (giver, turn-in, prerequisite, breadcrumb, objective, XP, races), an NPC's or object's place or rank, a wrong drop | `forever-db/corrections/` |
| how a quest is done (an item from a chest, a delayed offer, an object to click) | `data/mechanics-public.json`, under `corrections` |
| whether the route takes a quest, or an order players asked for | `data/route-fixes.json` (`overrides` or `deliberate`, with `reason` and `issue`) |
| a step's tip or level gate | `data/guide-fixes.json` |
| an arrow point (where an objective is done, where a giver or ender stands) | `data/places.json` |

Check the records with `forge data check-corrections`, then go on to step 4.
The rest of this step is for hand-edited guides.

- Look up every quest, NPC, object and item id, and every inn and flight
  point name, with `polestar find` before writing it. Never write one from
  memory: Forever's ids and givers differ from Classic.
- Leave out what the compiler fills in. `accept 184` is enough: the title,
  giver and coordinates come from the data. Type coordinates only for
  `goto`, `explore` or a place the data does not know.
- When the guide is wrong because the data is (a giver, a spawn, a drop),
  correct `forever-db/corrections/` as well, so Forge and the next
  route refresh see it.
- Change only what the fix needs: no reformatting, and no "while I'm here"
  edits to other steps.

## 4. Pin it with a test

Add a case to `tests/guides-reported.test.js` (cave mouths go in
`tests/guides-caves.test.js`). It checks what the player gets, such as the
goal order or where the arrow leads, never the guide's wording. Name the
report in the test's title, following the cases already there. On a
hand-edited guide the test fails on the old guide and passes on the fixed
one. For a record fix to a generated guide the written guide changes only
when the maintainer builds: the test may still fail locally, so say so in the
pull request; the build's ledger marks it `undone` if the build does not
deliver it.

## 5. Check it

```sh
forge guide lint
polestar playtest --filter <guide file or id>
node --test tests/guides-reported.test.js  # or tests/guides-caves.test.js for a cave mouth
```

You don't need the whole suite; CI runs it on your pull request and tells
you if anything else broke.

**Do not commit `addon/Polestar_Guides/Guides.lua`.** The maintainer runs
`polestar regen` after merge. Never edit it by hand or splice in a hunk
from another compile: a spliced hunk can load without error while the game
never sees the goals it contains.


## 6. Changelog and commit

- The changelog entry is a fragment in `changes/`, never an edit to
  CHANGELOG.md. It goes under "For players": say what the player sees now,
  and credit the reporter by the name they reported under:

  ```sh
  forge changelog add players --name <guide>-<what> --text "<entry> (thanks Tom)."
  forge changelog check
  ```

  The release puts it under its version.
- One change per commit. The message is written for the player:
  "Westfall: turn in at Sentinel Hill before the farms", not "fix step 13".

## 7. The pull request

- Base it on the branch from step 1. The template asks for the verdict and
  its evidence, and which checks ran and which did not.
- Issues: write "closes #N", once for each issue the pattern fix covers.
  That is what lists the pull request on each issue.
- Tick the AI-agent checkbox and fill in "Model and tool: <model name and
  version> via <app or CLI>" (for example "Claude Sonnet 4.6 via Claude
  Code"). The person running the agent reads the diff and the description
  before opening the pull request.
