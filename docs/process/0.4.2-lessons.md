# What 0.4.2 taught us about testing

0.4.2 shipped on 21 November 2026 with regressions against 0.4.1.1 that
players and a post-release audit found within a day: lifts never showed
(#3452), quest targets on the other faction's ground were refused
(#3447), Ban'ethil Barrow Den's chest was never reached (#3449), the route
in Shen'dar Village swapped between a portal and the walk (#3450), a new
step's first walk could show no bearing for 10-30 seconds (#3448), and an
update mid-guide could open the guide stops behind where the player was
(#3440: 28 of 195 tested points, 1 to 88 steps back). All of them were
fixed in 0.4.2.1 and 0.4.2.2. This page is why they got past us, and what
changed so the next ones don't.

## Why they were found late

- **The suites that need data were skipped in CI.** `data/forever` is not
  in the repository, so every test that reads it skips on a pull request
  (docs/CI.md, "Reference data on GitHub"). The guide suites and the
  playtests ran only on the maintainer's machine, in batches, after the
  code had merged.
- **Pull requests were tested alone and met each other first on `next`.**
  127 pull requests merged in the three days between 0.4.1.1 and 0.4.2.
  Each was green against `next` as it stood when its CI ran; what they did
  together was first run after they had all merged.
- **Nobody played it the way a player does before the tag.** The tests
  checked rules one at a time. No one walked the real stretches (a lift, a
  barrow, a town of the other faction, the first steps after an update)
  on the candidate side by side with the release players had, which is
  how the audit after the release found them.
- **Forever gives addons no height.** Every 0.4.2 bug report shows the
  player at height 0: on Forever the game's position call returns 0 for it.
  0.4.2's lift rule waited until the player was on the deck, judged by
  height, so it passed every test (which had heights) and never fired in
  the game.

## What changed

- **CI runs the data suites** (#3310, being done for 0.4.3): a faster CI
  with the data pack available to it, so a pull request meets the guide
  suites before it merges, not after.
- **Smaller releases.** A patch ships what is ready and the rest moves to
  the next one (0.4.2.2 moved 9 unfinished issues to 0.4.3 rather than wait
  for them), so fewer changes meet each other for the first time in one
  build.
- **An arrow checklist** (the arrow behaviour inventory, ARROW-INVENTORY):
  every arrow, walk, route-line, ride and arrival behaviour shipped since
  0.2, one row each, with the changelog entry that shipped it, how a
  player notices it missing, and a check to run. It is re-run on every
  release candidate against the live release, at height 0 first as the
  game gives it; a row that regresses blocks the release until it is fixed
  or ruled by design.
- **A "first five minutes" check** on every release candidate: a fresh
  install and an update in the middle of a guide, played from login. The
  guide opens at the right step, the arrow points, the first walk starts,
  no errors. #3440 was found this way.
- **The in-client perf report.** `/polestar perf report` times Polestar's
  own work in the player's game and gives it in a box to copy; a stutter
  report carries it, so a slowdown is measured on a real client instead of
  guessed from the test harness.
